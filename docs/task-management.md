# 任务管理与 Codex 自动跟踪

会话管理支持备注、标签、重要标记和手动状态。信息由主服务保存，多个设备共享；自动观察不会修改手动状态，也不会启动、停止或重放终端任务。

## 配置 Codex 跟踪

1. 在“节点管理”中，针对需要跟踪的节点选择“启用 Codex 跟踪”。节点会为 **Agent 所在的系统账户**合并用户级 `hooks.json`，保留其他 Hook；如果已有配置，修改前会在节点私有数据目录备份。自定义 `CODEX_HOME` 必须与 Agent 的设置一致。
2. 在该账户的 Workdeck 终端中启动 `codex`，运行 `/hooks`，审核并信任 Workdeck 的 Hook。Codex 对非托管 Hook 的信任检查不会被 Workdeck 绕过。各账户各节点分别配置和信任；非 Agent 账户的历史终端如果无法访问 Agent 的私有数据目录，暂时只能显示状态未知。
3. 信任后直接运行 `codex` 即可。已经运行的 Codex 是否加载新配置由 Codex 决定，不能保证动态接入；必要时在自然结束后退出并恢复会话，Workdeck 不会主动关闭它。节点管理可移除 Workdeck 的 Hook，保留其他配置；已启动的进程可能继续使用已加载配置。

## 状态与通知

终端标签、概览卡片和终端底栏显示最近的 Codex 状态；没有可信事件时不作推断。节点只读检查终端进程树中的进程名和父进程 ID，发现 Codex 时可提示“已检测到，状态未知”；进程检查不读取命令参数或终端内容，不能保证发现被隔离或脱离终端的进程。节点离线或终端不再运行时，历史状态显示为未知。节点将事件写入私有目录并主动上报，连接恢复时重新同步；浏览器通过事件流更新，轮询作为回退。浏览器通知默认关闭，需要在设置中授权；页面关闭、未登录或浏览器未运行时不推送。首次打开页面不补发历史通知。

“可能需要处理”对应权限请求等事件；其他 Hook 可能自动处理请求，因此用户应打开终端确认。停止事件意味着 Codex 到达一轮的停止环节；其他 Hook 可能要求继续，本轮结束不证明整个目标成功。完成通知会短暂等待并核对当前事件，但仍不能保证后续不会继续。节点只保存最近状态，极短时间内连续发生的事件可能合并，通知不是完整审计记录。中断、异常退出或 Hook 未获信任时，状态可能不完整或过期。不会通过解析屏幕文字猜测。

Workdeck 只保存事件类型、哈希标识和时间，不保存 Hook 输入中可能包含的提示词、模型回复、工具参数或对话记录。旧版节点和此前的启动命令仍可兼容，但普通 `codex` 自动跟踪需要新版 Agent。Codex 重启、节点重启、不同权限账户和多进程场景不能保证完整的事件追溯。

参考：[Codex Hooks 与信任审核](https://learn.chatgpt.com/docs/hooks)。
