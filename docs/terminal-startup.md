# 终端首屏连接流程

点击未打开的终端时，浏览器挂载 xterm 并立即发起 WebSocket；已打开的标签直接切换已有视图。浏览器请求仍需通过主服务完成登录校验和写入权限分配。

## 节点预连接

支持预连接的主服务在控制通道下发配置。节点维护两条空闲、经过节点签名认证的 WebSocket。用户打开终端时，主服务优先分配空闲连接，通过原控制通道依次确定写入归属，并在预连接上绑定目标终端。节点确认绑定后附着到已有 tmux 会话，同时后台补充空闲连接。没有空闲连接、连接失效或节点版本不支持时，自动使用原有按需建连流程。

空闲连接只发送心跳，不附着终端，不读取或缓存后台终端输出。用户关闭页面只关闭查看连接，tmux 进程继续运行。节点控制通道断开时，其空闲和已分配连接一并清理，节点重连后重新准备。并发查看仍保持单个写入者；写入归属在控制通道中排序，避免不同预连接上的绑定顺序导致旧连接覆盖新连接的写入权限。

这消除了节点到主服务的新建 TCP/TLS/WebSocket 握手等待，但浏览器到主服务仍需要建立连接。预连接不能修复浏览器所在网络的公网连接问题。

## 首屏与链路优化

终端输出通过可用的 WebSocket 立即显示；WebRTC 在首次输出渲染后后台检测，检测成功再按链路策略切换。节点到主服务的连接沿用公网与可用 Tailnet 路径竞争，TLS 仍校验原主服务域名。

## 分段计时

主服务日志的 `terminal startup` 行关联一个随机 `trace`，记录收到浏览器请求、分配预连接或通知节点建连、节点数据连接到达、收到第一批终端输出等阶段。新版浏览器额外上报 WebSocket 打开、节点 ready、实际首屏渲染的耗时；等待超过五秒时上报一次尚未完成的阶段。

计时只包含随机关联标识、阶段和毫秒数，不记录终端内容、目录、地址或登录凭证。上报接口需要有效登录和 CSRF 校验，上报失败不阻塞终端。浏览器完成 TCP/TLS 握手之前的等待仅能由浏览器计时体现，不能用 Hub 收到请求之后的耗时代替。

## 浏览器连接握手卡住时

浏览器建立 WebSocket 超过 500 毫秒仍未打开时，最多补发一个连接尝试，先打开的连接获胜，另一条立即关闭。两次尝试均未打开时在 8 秒后结束本轮，由现有重连退避机制恢复；页面关闭时两条尝试和相关计时器一起清理。

竞争连接带有 `deferred=1`，主服务在收到获胜浏览器的 `start` 消息后才分配写入权限和节点连接。没有获胜的尝试不能抢占控制权、附着 tmux 或消耗节点预连接。旧版客户端继续使用原流程。该机制只针对浏览器握手阶段，不会为已打开的终端重复传输数据。

随机连接流量在部分网络路径上可能遇到 TCP 握手返回包丢失，短延迟补发只能降低这类故障对首屏的影响，不能修复底层网络。应结合客户端与服务器两端的 SYN/SYN-ACK 证据定位，不能仅凭浏览器的 WebSocket 尚未打开就断定 TCP 超时。

计时日志补充 `http_ingress`（登录校验之前）、`browser_selected`、`client_closed` 与 `close_code`，区分请求尚未到达主服务、服务端校验、未获选的竞争连接，以及用户主动关闭。`close_code=-1` 表示上报时尚未收到 WebSocket 关闭事件。

## WebSocket 持续无法握手时的 HTTP 回退

连接开始 150 毫秒后，如果 WebSocket 尚未打开，浏览器并行尝试同源 HTTP 流。它可以复用浏览器现有的 HTTP/2 或 HTTP/3 HTTPS 连接，避免终端必须等待一条新的 WebSocket TCP 连接。最快可用的通道获胜，其余尝试全部关闭；在旧浏览器或网络不支持复用时，HTTP 本身也可能需要新建 TCP 连接，因此这不是网络故障的绝对保证。

HTTP 回退采用 `GET /api/terminals/{id}/stream` 的 SSE 下行与 `POST /api/terminal-streams/{stream}/input` 的有序批量上行。数据包携带类型及 Base64 编码的字节；上行按顺序提交，避免命令、粘贴与控制消息乱序。写入请求超时或失败会关闭该查看连接并触发原有重连，不自动重发可能已经执行的输入。大批量输出有 Base64 编码开销，这条路径主要保障可用性。

HTTP 与 WebSocket 共用终端转发、只读、接管、退出登录撤销、节点预连接与 WebRTC 检测逻辑。HTTP 流 GET 额外校验 CSRF，上行流标识绑定到创建该流的登录会话；其他设备的有效登录也不能往该流注入输入。关闭页面会取消 HTTP 流、在途输入请求及未获选连接，主服务清理对应流注册，不关闭 tmux 进程。每个登录最多 64 条 HTTP 流，主服务最多 1024 条。

网络面板会明确显示“HTTP 流式中转”，不会将其标成 WebSocket。切到 WebRTC 后仍保留中转通道作为授权和回退通道，当前链路及延迟比较继续按实际通道统计。
